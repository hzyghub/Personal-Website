§ 1

背景 Background

城市轨道交通是典型的数据生产企业——AFC售检票系统、ACC清算系统、设备监控系统每天自动产生海量结构化数据，数据采集基础设施已经成熟。但数据只是沉睡在数据库里，无人问津。业务人员不会写SQL，只能靠导出Excel做浅层汇总，客流模式、设备关联、异常预警这些深层价值无人挖掘。缺的不是数据，是一个能让不懂技术的人用自然语言查询数据、让数据主动服务业务决策的智能分析层。 Urban rail transit is a classic data-producing industry — AFC ticketing systems, ACC clearing systems, and equipment monitoring systems automatically generate massive structured data daily. The data collection infrastructure is mature. But the data just sits dormant in databases, untouched. Business staff can't write SQL — they can only export Excel for shallow summaries, while deep-value insights like passenger flow patterns, equipment correlations, and anomaly warnings go unmined. What's missing isn't data; it's an intelligent analysis layer that lets non-technical people query data in natural language and makes data actively serve business decisions.

具体来说，是某新开通线路——多个站点、日均数万乘次、千万级年客运量。四个交易来源（AFC系统交易、二维码、城市一卡通、交通联合卡）各自有独立的数据库和字段格式，没有统一的分析视图。其中二维码占一半以上，城市一卡通和交通联合卡各占约两成和一成多，单程票不到2%。更棘手的是，二维码交易占全部流水的一半以上，但它只有独立的进出站记录，没有直接的起讫点（OD）信息——出行轨迹需要配对算法来重建。这些数据本来就在那里，只是没有被理解。 Specifically, a newly opened line — multiple stations, tens of thousands of daily rides, tens of millions of annual trips. Four transaction sources (AFC system transactions, QR codes, city transit cards, national transit cards) each had their own databases and field formats, with no unified analytical view. QR codes accounted for over half, city and national transit cards roughly 20% and 10%+ respectively, single-use tickets under 2%. The bigger challenge: QR code transactions accounted for over half of all records but only had independent entry/exit events with no origin-destination (OD) pairs — travel patterns had to be reconstructed via a pairing algorithm. The data was already there; it just wasn't being understood.

§ 2

方案 Solution

整体思路。方案不是再建一套SaaS系统，而是在已有的AFC/ACC数据基础设施之上，搭建一个智能分析层。技术架构是 FastAPI + React + DuckDB，支持自然语言查询（Text-to-SQL），适配 9 个主流 LLM 厂商。 Overall approach. The solution wasn't to build another SaaS system, but to create an intelligent analysis layer on top of the existing AFC/ACC data infrastructure. Built on FastAPI + React + DuckDB, supporting natural language queries (Text-to-SQL), compatible with 9 major LLM providers.

数据层。选用了DuckDB——一个嵌入式列式分析数据库。对于离线分析场景，它比SQLite更快（列式扫描），比PostgreSQL更轻（无需服务器），单文件即可承载40多张表、数百万条交易记录。整个ETL管道设有6个检查点，每步暂停等待人工确认数据正确性后才继续。 Data layer. DuckDB — an embedded columnar analytics database. For offline analysis, it's faster than SQLite (columnar scans) and lighter than PostgreSQL (no server needed). A single file holds 40+ tables and millions of transaction records. The ETL pipeline has 6 checkpoints, each pausing for manual data verification before proceeding.

核心算法。二维码OD配对是最大的技术挑战。系统通过哈希用户ID关联同一人的进出站记录，再以180分钟时间窗口过滤合理行程，最终取每笔进站对应的最早出站记录。这套算法需要在百万级二维码记录中找到正确的配对，目标成功率超过80%。 Core algorithm. QR code OD pairing was the biggest technical challenge. The system links entry/exit records by hashed user IDs, filters with a 180-minute time window for reasonable trips, then selects the earliest exit for each entry. This algorithm must find correct pairs among millions of QR code records, targeting an 80%+ success rate.

AI问答。采用规则型Text-to-SQL，而非让LLM直接生成SQL。这是MVP阶段的务实选择——关键词匹配预设模板，保证SQL正确性、零token成本、确定性结果。9家LLM厂商通过统一的OpenAI兼容适配器接入，因为中国LLM市场的API已趋同于OpenAI协议标准。但Text-to-SQL只是起点——平台的终极目标是Level 4级智能体：能跨表关联客流、设备、故障、维护数据，自动执行多步分析，给出综合结论和运营建议。 AI Q&A. Rule-based Text-to-SQL instead of having LLMs generate SQL directly. This is a pragmatic MVP choice — keyword matching to predefined templates ensures SQL correctness, zero token cost, and deterministic results. 9 LLM providers connect through a unified OpenAI-compatible adapter, as China's LLM market has converged on the OpenAI protocol standard. But Text-to-SQL is just the starting point — the platform's ultimate goal is a Level 4 agent: capable of cross-referencing passenger flow, equipment, fault, and maintenance data, automatically executing multi-step analysis, and delivering comprehensive conclusions with operational recommendations.

功能模块。MVP包含8个功能模块：OD分析（弦图、Sankey流程图、站点排名）、时段热力图（站点×小时矩阵、峰值检测）、设备负载分析（闸机/售票机负载分级、运维建议）、换入客流分析（源站/线路/时段四维分析）、新航站楼专项（航站楼间客流转移对比）、设备故障分析（数万条真实故障记录、部件分布、严重程度分级）、ACC线网报表集成（十余种官方报表自动导入、断面流量和精确换乘量等新指标）、AI智能问答。 Functional modules. The MVP includes 8 modules: OD analysis (chord diagrams, Sankey flow charts, station rankings), time-slot heatmaps (station × hour matrix, peak detection), equipment load analysis (gate/ticket machine load grading, maintenance recommendations), transfer-in passenger analysis (4-dimensional: source station/line/period/ticket type), New terminal expansion analysis (inter-terminal flow transfer comparison), equipment fault analysis (tens of thousands of real fault records, component distribution, severity grading), ACC network report integration (over a dozen official report types auto-imported, adding metrics like cross-section flow and precise transfer volume), and AI Q&A.

ACC报表集成。Phase 4的核心成果。ACC（自动售检票清算中心）提供十余种官方报表，涵盖OD统计、断面流量、换乘量、出行特征等。系统自动导入后生成多张ACC数据表，带来传统AFC数据无法提供的新指标——精确换乘量、平均出行距离（公里）、平均乘站数、平均出行时间（分钟）。系统还实现了ACC与AFC数据的逐站对比，差异超过5%自动标记异常。 ACC report integration. The core deliverable of Phase 4. The ACC (Automated Fare Collection Clearing House) provides over a dozen official report types covering OD statistics, cross-section flow, transfer volume, travel characteristics, and more. Auto-import generates multiple ACC data tables, adding metrics unavailable from AFC data alone — precise transfer volume, average travel distance (km), average station count, average travel time (min). The system also cross-references ACC vs AFC data station by station, auto-flagging anomalies where discrepancies exceed 5%.

数据安全。所有个人标识信息在导入前完成脱敏：卡片号码MD5加密（不可逆）、时间截断到小时（移除分钟秒）、操作员编号掩码处理（如OP1234变为OP**34）。分析环境与生产环境物理隔离，数据全程离线处理，不上传任何云服务，符合网络安全法、数据安全法和个人信息保护法的要求。 Data security. All personally identifiable information is anonymized before import: card numbers are MD5-hashed (irreversible), timestamps truncated to the hour (removing minutes and seconds), operator IDs masked (e.g., OP1234 becomes OP**34). The analysis environment is physically isolated from production, with all data processed offline and never uploaded to any cloud service, complying with the Cybersecurity Law, Data Security Law, and Personal Information Protection Law.

§ 4

反思 Reflections

作为一个非专业软件工程师的轨道交通运营业务专家，我在14天内完成62次Git提交，独立搭建了包含8个功能模块、35个API、40多个前端组件的平台。能做到这件事，靠的不是编程能力——AI完全不懂轨道交通业务，不可能自己推导出"二维码为什么需要OD配对"或"AFC和ACC的数据为什么会对不上"。真正让AI能正确执行的前提，是我前期花大量时间创建的业务资料：项目立项文档、业务逻辑手册、数据导出操作规程、系统设计方案、业务术语速查手册、100多个专业术语的定义。这些领域知识加上一份603行的协作规范（CLAUDE.md），才构成了AI能正确工作的完整上下文。 As a rail transit operations domain expert (not a professional software engineer), I completed 62 Git commits in 14 days, solo-building a platform with 8 modules, 35 APIs, and 40+ frontend components. The key wasn't programming skill — AI knows nothing about urban rail transit operations and can't deduce on its own why QR codes need OD pairing or why AFC and ACC data might not reconcile. What truly enabled AI to execute correctly was the substantial upfront work of creating domain materials: project charter, business logic manuals, data export procedures, system design documents, a business terminology reference with 100+ specialized term definitions. These domain knowledge assets, combined with a 603-line collaboration spec (CLAUDE.md), formed the complete context AI needed to work correctly.

举一个具体的例子。二维码进站记录和出站记录是分开的，没有直接的起讫点（OD）信息。对我来说这是常识——轨道交通行业的所有人都知道二维码要配对。但对AI来说，它根本不知道什么是"进站"什么是"出站"，更不知道为什么要把它们配起来。我得把这个"常识"写出来：同一个用户（哈希ID相同）、进站时间在出站之前、间隔不超过180分钟、取最早的出站记录——这就是一个完整的知识规格化过程。脑子里的一秒钟判断，变成了AI能执行的明确规则。整个项目里，这样的"常识转化"有几十个。 Here's a concrete example. QR code entry and exit records are stored separately, with no direct origin-destination (OD) pairs. For me this was obvious — everyone in urban rail transit knows QR records need pairing. But AI doesn't know what "entry" or "exit" means, let alone why they need pairing. I had to write down this "common sense": same user (matching hashed ID), entry before exit, time gap under 180 minutes, take the earliest exit record — that's the complete knowledge specification process. A one-second judgment in my head became an explicit rule AI could execute. There were dozens of these "common sense translations" throughout the project.

这个经验催生了IntentBridge方法论。它包含两层：协作规格告诉AI怎么工作，知识规格告诉AI判断所需的领域依据。两层缺一不可——只有协作规格没有知识规格，AI不知道依据什么做判断；只有知识规格没有协作规格，AI不知道怎么使用这些知识。当你的领域知识足够深、但编程能力有限时，两层规格的质量直接决定了AI能帮你走多远。 This experience gave birth to the IntentBridge methodology. It comprises two layers: collaboration specs tell AI how to work, and knowledge specs provide the domain basis for AI's judgments. Both are indispensable — collaboration specs without knowledge specs leave AI without a basis for judgment; knowledge specs without collaboration specs leave AI unsure how to use that knowledge. When your domain expertise runs deep but your coding skills are limited, the quality of both layers directly determines how far AI can take you.

整个开发经历了5个阶段：从ETL管道和DuckDB基础设施起步，到OD分析和热力图等核心分析模块，再到换入客流和新航站楼专项等专项扩展，然后是ACC线网报表集成，最后是AI智能问答。MVP验证了技术可行性，下一步的目标是把AI从当前的单轮问答推进到Level 4——一个能自主跨表关联、多步推理、给出综合运营建议的智能体。 Development went through 5 phases: starting with the ETL pipeline and DuckDB infrastructure, then core analysis modules like OD analysis and heatmaps, specialized expansions for transfer analysis and new terminal, ACC network report integration, and finally AI Q&A. The MVP validated technical feasibility. The next goal is evolving AI from single-turn Q&A to Level 4 — an agent capable of autonomous cross-table correlation, multi-step reasoning, and comprehensive operational recommendations.
