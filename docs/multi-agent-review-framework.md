# 多角色AI审查框架

> 起源：2026-04-18，对 hzy-site v3.0 进行的六角色审查实验
> 状态：产品雏形 v0.3

## 为什么要这样做

真实的反馈极其稀缺。社交顾虑让周围的人说好话，自我审查有盲区，专业评估要花钱且难以获得多维度的交叉验证。

多角色AI审查的核心价值：

1. **无社交顾虑的诚实反馈** — AI不需要维护关系，可以直说
2. **多视角交叉验证** — 多个角色独立指出同一个问题 = 高置信度盲区
3. **低成本高密度** — 一次获得6个专业视角的评价，现实世界中很难组织
4. **发现"不知道自己不知道"的东西** — 不同角色天然关注不同维度

## 审查对象与角色模板

不同审查对象需要不同的角色组合。以下是经过验证的角色模板：

### 模板一：个人网站 / 作品集审查

| 角色 | 关注点 | 评估重点 |
|------|--------|---------|
| 技术面试官 | 技术深度、问题解决能力 | 项目描述是否有真实的技术判断，还是泛泛而谈 |
| 行业同行 | 专业度、行业对话能力 | 能不能用行业通用语言交流，自创术语是否有价值 |
| 目标用户 / 潜在客户 | 可理解性、实用价值 | 非专业人士能不能看懂，能拿走什么 |
| 潜在雇主 / 投资人 | 商业价值、人才价值 | 值不值得约聊，风险点在哪 |
| 设计专业人士 | 视觉、体验、信息架构 | 排版、配色、阅读体验、交互质量 |
| 猎头 / 人才中介 | 市场定位、竞争力 | 在候选人池中的差异化，薪资区间，匹配什么岗位 |

### 模板二：简历审查

| 角色 | 关注点 | 评估重点 |
|------|--------|---------|
| HR筛选者 | 30秒扫描，过不过 | 关键词匹配度、格式是否专业、履历是否有明显断层 |
| 技术面试官 | 技术描述的真实性和深度 | 技术名词是堆砌还是真正理解，项目描述能否经得起追问 |
| 未来同事 | 能不能一起干活 | 沟通风格是否清晰、有没有协作意识、技术品味是否合拍 |
| 管理层（汇报对象） | 能不能放心交办任务 | 是否有主人翁意识、能不能独立推进、遇到问题会不会主动沟通 |
| 猎头 | 市场竞争力、薪资定位 | 在同级别候选人中的差异化、跳槽动机是否合理、市场定价区间 |

### 模板三：BP / 产品方案审查

| 角色 | 关注点 | 评估重点 |
|------|--------|---------|
| 投资人 | 市场规模、团队、壁垒、值不值得投 | 市场数据是否自洽、团队配置是否匹配目标、壁垒是真实的还是自我感觉 |
| 技术合伙人 | 能不能做出来、技术风险 | 技术路线是否务实、时间表是否合理、有没有被忽视的技术难点 |
| 目标用户 | 想不想用、痛点是否真实 | 问题描述能不能引起共鸣、解决方案是不是在解决真问题 |
| 竞争对手 | 护城河深不深、容不容易被抄 | 核心优势是否可复制、壁垒是时间积累的还是可以速成的 |

### 模板四：设计作品审查

| 角色 | 关注点 | 评估重点 |
|------|--------|---------|
| 设计总监 | 视觉品质、设计思维、细节把控 | 排版是否有网格意识、配色是否有体系、细节处理是否到位 |
| 产品经理 | 是否解决真实问题、交互逻辑 | 设计是否服务于功能、信息层级是否清晰、操作路径是否合理 |
| 目标用户 | 第一感受、能不能用明白 | 不看说明能不能理解核心功能、视觉风格是否产生信任感 |
| 客户（甲方） | 是否满足需求、值不值这个价 | 设计有没有回应brief的核心诉求、交付完整度如何 |
| 同行设计师 | 专业技法、创新性 | 工艺细节是否成熟、有没有自己的设计语言、还是模板感太重 |

## 评分维度

维度分两层：**基础维度**（所有场景必用）+ **场景维度**（按审查对象选配）。

### 基础维度（必用）

| 维度 | 说明 | 分值 |
|------|------|------|
| 第一印象 | 30秒内的直觉判断 | 1-5 |
| 可信度 | 信息是否真实、是否可验证 | 1-5 |
| 会 / 不会推荐 | 最终判断 | 是/否 + 原因 |

### 必答问题（不计分，必须回答）

- **改进空间**：最需要优化的 Top 3，每个附具体建议

### 场景维度（按模板选配）

| 模板 | 额外维度 |
|------|---------|
| 网站/作品集 | 专业深度、独特性、视觉体验 |
| 简历 | 技术真实性、市场竞争力、沟通清晰度 |
| BP/方案 | 市场验证、可行性、壁垒 |
| 设计作品 | 视觉品质、交互逻辑、创新性 |

每个场景维度同样用 1-5 分制。

## 操作步骤

### 审查规模选择

不是每次都要跑全套。根据需求选规模：

| 规模 | 角色数 | 适用场景 | 预估消耗 |
|------|--------|---------|---------|
| 轻量 | 2-3个 | 快速验证一个具体修改、确认方向是否对 | 每个角色约2000-4000 token |
| 标准 | 4-6个 | 首次审查、重要交付前的全面检查 | 每个角色约3000-6000 token |
| 深度 | 6+个 | 重大决策前的穷尽式审查（罕见需要） | token消耗大，评价可能重复 |

**什么时候不需要多角色审查：**
- 改了一个错别字/调了一个颜色 → 自己检查就够了
- 已经跑了3轮以上 → 剩余问题通常靠单角色确认即可，不必全套重跑
- 只想确认某个具体点 → 开一个对话问就行

**什么时候值得跑：**
- 首次对外展示前的全面检查
- 大改之后的重新评估
- 对自己作品的水平没有把握时

### Step 0：准备工具

三种执行方式，任选其一：
- **Claude Code**：用 `Agent` 工具并行启动多个 agent，每个 agent 跑一个角色
- **ChatGPT / Claude 网页版**：开多个独立对话窗口，每个窗口跑一个角色
- **任何支持多轮对话的 AI**：逐个对话，每次只给一个角色的 prompt

**关键规则：不要在同一个对话里跑多个角色。** 后续角色会看到前面的评价，破坏独立性。每个角色必须是全新的对话上下文。

### Step 1：准备审查材料

AI只能审查它能看到的材料所覆盖的方面。给什么材料，决定能审什么维度：

| 给AI什么材料 | 能审查什么 |
|-------------|-----------|
| 完整文本 | 内容质量、逻辑结构、表达清晰度、信息密度 |
| GitHub 代码仓库 | 架构设计、代码质量、项目结构、API设计、安全实践 |
| Figma / 设计截图 | 视觉层次、排版、配色、信息架构、组件一致性 |
| 实际产品 URL | 静态页面内容和视觉，但交互体验（动画、加载速度、操作手感）无法感知 |
| 文档 / BP / PPT | 叙事逻辑、论据支撑、可理解性、说服力 |

**同一个审查对象可以给多种材料。** 比如审查一个app项目，同时给代码仓库 + 截图 + README，AI就能从架构、视觉、叙事三个维度评价。给的材料越充分，审查维度越完整。

### Step 2：选择角色模板 + 编写人设

根据审查对象选择对应模板（见上方"审查对象与角色模板"）。也可以根据具体情况自定义角色。

**角色人设必须包含三层信息：**

1. **身份标签**（1句话）— "你是一个大厂技术总监，15年以上经验"
2. **核心经验/视角来源**（1-2句话）— "面试过上千人，见过太多包装精美但内容空洞的个人网站"
3. **评判倾向**（1句话）— "你最关注能不能解决真实问题，最反感空谈概念"

人设深度直接决定评价质量。浅的人设得到"还不错"的废话评价，深的人设得到尖锐的具体反馈。

**示例（技术面试官完整人设）：**
```
你是一个大厂技术总监，15年以上经验，面试过上千人。
你关注"能不能解决真实问题""有没有深度思考""技术实力到底如何"。
你见过太多"包装精美但内容空洞"的个人网站，你的评判标准是：
项目描述是否有真实的技术判断力，还是网上抄一段教程能写出来的东西。
```

### Step 3：逐个启动Agent

给每个agent的prompt结构：

```
你扮演 [角色名称]。

[身份标签 — 1句话]
[核心经验/视角来源 — 1-2句话]
[评判倾向 — 1句话]

请从你的视角审查以下 [审查对象类型]：
[审查材料]

评估维度：
- 第一印象（1-5分）
- 可信度（1-5分）
- [场景维度1]（1-5分）
- [场景维度2]（1-5分）
- 你会/不会推荐？为什么？

必答问题：
- 改进空间（Top 3，每个附具体建议）

场景维度根据模板选配（见"评分维度"章节）。

要求：
- 直接、真实、不客气。你不是在鼓励他，你是在评估他。
- 每个评分必须附具体例子——"扣1分因为xxx"而非"还可以"。
- 至少指出3个具体问题。不允许纯正面评价，即使整体很好也必须找到改进空间。
- 如果某个维度你无法判断，写"无法判断：[原因]"，不许跳过也不许猜。
```

### Step 4：汇总分析

等所有角色评价完成后：

**4a. 质量检查** — 先检查每个角色的评价质量：
- 是否有具体例子支撑每个评分？
- 是否至少指出了3个问题？
- 是否全是正面评价？
- 标记缺少具体例子或全是正面的评价为"低质量评价"，在后续分析中降低权重。

**4b. 共识提取** — 判断"相同问题"的粒度：

共识分三个层级：
- **强共识**（3+角色，措辞不同但指向同一核心问题）— 如"定位偏高""自我拔高""过于自信"，措辞不同但核心一样。**高置信度盲区，优先修复。**
- **弱共识**（2角色，角度相似）— 可能是真问题也可能是巧合，需要你判断。
- **伪共识**（2+角色用了相同的词，但指向不同问题）— 需要仔细区分。

判断方法：**不要看"用了什么词"，看"指向什么核心问题"。** 如果不确定，把各角色的原文放在一起对比。

**4c. 分类整理** — 将改进建议分为三类：
1. 应该做（高共识 + 可执行）
2. 不该做（不属于当前范围 / 过度优化）
3. 不是这件事能解决的（是更大的问题）

### Step 5：输出最终报告

汇总分析完成后，整理为最终交付物：

```markdown
# [审查对象名称] — 多角色审查报告

> 审查日期：[日期] | 角色数量：[N] | 框架版本：v0.3

## 共识发现（高置信度）
[强共识问题，按严重程度排序]

## 各角色评价摘要
[每个角色一段：角色名 + 核心判断（1-2句）+ 代表性引文]

## 改进优先级

### 立即改
[高共识 + 可执行]

### 后续考虑
[高共识但不属于当前范围]

### 不是这次的事
[更大的问题]

## 详细评价
[各角色完整评价原文，按角色分节]
```

### Step 6：决策与执行

- **共识度高 + 可执行** = 立即改
- **共识度高 + 不属于当前范围** = 记录，后续考虑
- **只有一个角色提到** = 评估是否值得改
- **角色之间意见矛盾** = 根据自己的判断取舍

## 设计原则

1. **角色独立** — 每个agent不知道其他角色的评价，避免从众
2. **强制评分+理由** — 不许只说好话，必须给出扣分原因和具体例子
3. **共识提取** — 多个角色独立指出的问题 = 真盲区，单个角色的问题可能是偏好
4. **区分"该改"和"不改"** — 不是所有反馈都要执行，区分可执行建议和范围外建议
5. **诚实优先** — 明确要求"直接、真实、不客气"

## 已知局限

- **AI评AI** — AI的评价本身有模型偏见，不是人类真实反馈的完美替代
- **无法验证真实性** — AI无法查证你声明的事实是否真实，只能评估"是否自洽"
- **文化偏差** — 模型对中文职场语境的理解可能不够精准
- **单次快照** — 审查的是某个时间点的状态，不是持续反馈

## 审查能力边界

审查对象没有类型限制——网站、简历、代码、BP、设计稿、产品，都能审。**限制不在对象类型，在材料。** 给代码就能审代码，给截图就能审视觉，给文档就能审叙事。

真正的硬限制只有三条：

- **专业领域判断不可信** — 医疗诊断、法律意见、财务建议，AI的评价不能替代专业资质的人的判断
- **实物体验无法替代** — 建筑空间感、服装面料手感、食品口感，AI没有感官
- **交互手感无法感知** — 动画流畅度、操作响应速度、触觉反馈，AI只能看代码和截图，不能"用"
